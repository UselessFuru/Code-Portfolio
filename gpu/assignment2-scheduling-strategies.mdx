Assignment 2 asks a fundamental GPU design question: **how should work be divided among threads
when the number of threads doesn't exactly equal the amount of work?** Three different kernel
strategies are implemented and run simultaneously on the same 10,240-element array multiplication
problem (`c[i] = a[i] * b[i]`), and all three must produce identical results.

Arrays are populated with:
```cuda
a[i] = 2 * i;       // 0, 2, 4, ... 20478
b[i] = (2 * i) + 1; // 1, 3, 5, ... 20479
```

<Info>
  The array size of 10,240 is not a power of two and is larger than the maximum threads per
  block (1,024 on most CUDA devices). This forces the programmer to think carefully about how
  threads loop over data.
</Info>

## Strategy Comparison

<Tabs>
  <Tab title="Solution 1 — Non-Cyclic (Block Partition)">
    ### Grid: 2 blocks × 1,024 threads

    Each block is assigned a **contiguous chunk** of the array. Block 0 owns indices 0–5119;
    Block 1 owns indices 5120–10239. Within its chunk, each thread strides forward by
    `blockDim.x` (1,024) to cover all elements assigned to that block.

    ```cuda
    __global__
    void matrixProductSol1(int *a1, int *b1, int *c1) {
        // create variables to keep track of when each block
        // begins and ends by dividing total array with the
        // number of blocks available
        int blockBegin = blockIdx.x * (arrSize / gridDim.x);
        int blockEnd   = blockBegin + (arrSize / gridDim.x);

        // each thread handles several elements in its block chunk
        // and jumps ahead by blockDim.x each time
        // this ensures threads dont do the same work
        for (int i = blockBegin + threadIdx.x; i < blockEnd; i += blockDim.x) {
            c1[i] = a1[i] * b1[i];
        }
    }
    ```

    **Thread coverage example (Block 0, 1,024 threads, 5,120 elements in chunk):**

    | Thread | First index | Second index | Third index | Fourth index | Fifth index |
    |--------|-------------|--------------|-------------|--------------|-------------|
    | 0      | 0           | 1024         | 2048        | 3072         | 4096        |
    | 1      | 1           | 1025         | 2049        | 3073         | 4097        |
    | ...    | ...         | ...          | ...         | ...          | ...         |
    | 1023   | 1023        | 2047         | 3071        | 4095         | 5119        |

    Each thread processes exactly 5 elements — all within its block's contiguous region.
  </Tab>

  <Tab title="Solution 2 — Cyclic (Round-Robin)">
    ### Grid: 2 blocks × 1,024 threads

    All 2,048 threads share the entire array, but each thread picks elements spaced
    `blockDim.x × gridDim.x` (2,048) apart — a **round-robin** distribution.
    Thread 0 handles elements 0, 2048, 4096, 6144, 8192; Thread 1 handles 1, 2049, 4097, …

    ```cuda
    __global__
    void matrixProductSol2(int *a2, int *b2, int *c2) {
        // global thread index variable to keep track of threads
        int globalThreadIdx = (blockIdx.x * blockDim.x) + threadIdx.x;

        // starts at the globalThreadIdx to keep track of individual thread
        // then increments by blockDim.x * gridDim.x (total threads in all blocks)
        // so that it covers the array cyclically without any overlaps
        for (int i = globalThreadIdx; i < arrSize; i += blockDim.x * gridDim.x) {
            c2[i] = a2[i] * b2[i];
        }
    }
    ```

    **Thread coverage example (2,048 total threads, 10,240 elements):**

    | Thread (global) | Iteration 1 | Iteration 2 | Iteration 3 | Iteration 4 | Iteration 5 |
    |-----------------|-------------|-------------|-------------|-------------|-------------|
    | 0               | 0           | 2048        | 4096        | 6144        | 8192        |
    | 1               | 1           | 2049        | 4097        | 6145        | 8193        |
    | ...             | ...         | ...         | ...         | ...         | ...         |
    | 2047            | 2047        | 4095        | 6143        | 8191        | 10239       |

    Every thread also processes exactly 5 elements, but the elements are **spread evenly
    across the entire array** rather than confined to a block-local region.
  </Tab>

  <Tab title="Solution 3 — Exact Mapping">
    ### Grid: 10 blocks × 1,024 threads = 10,240 total threads

    The grid is sized to **exactly match** the array: one thread per element. There is
    no loop — each thread computes exactly one product and exits.

    ```cuda
    __global__
    void matrixProductSol3(int *a3, int *b3, int *c3) {
        // global thread index variable to keep track of threads
        int globalThreadIdx = (blockIdx.x * blockDim.x) + threadIdx.x;

        // calculates the product of array a and array b and puts it
        // in array c
        c3[globalThreadIdx] = a3[globalThreadIdx] * b3[globalThreadIdx];
    }
    ```

    This is the simplest kernel and is functionally identical to Assignment 1. The
    trade-off is that it requires launching more blocks (10 instead of 2), which may
    not always be feasible when the data is much larger than the maximum grid dimensions.
  </Tab>
</Tabs>

## Non-Cyclic vs. Cyclic: Memory Access Pattern

The distinction between Solutions 1 and 2 matters for real-world performance:

| Property | Non-Cyclic (Sol 1) | Cyclic (Sol 2) |
|----------|-------------------|----------------|
| **Thread→element assignment** | Block 0 → indices 0–5119; Block 1 → 5120–10239 | Thread `t` → indices `t`, `t+2048`, `t+4096`, … |
| **Stride within a block** | `blockDim.x` (1,024) — threads in one block stay within the block's chunk | `blockDim.x × gridDim.x` (2,048) — threads span the full array |
| **Coalescing** | Within-block accesses are contiguous; inter-tile accesses skip | Adjacent threads always access adjacent memory addresses in each iteration |
| **Conceptual model** | "Assign a region to each block, then stripe within it" | "Stripe all threads across the whole array like a round-robin scheduler" |

<Note>
  In practice, cyclic scheduling often yields **better memory coalescing** because adjacent
  threads in a warp always access adjacent array elements (`t`, `t+1`, `t+2`, …) on every
  loop iteration, enabling the GPU to merge those accesses into a single memory transaction.
</Note>
